# Plan: F4 to F11 (built as one stack, on this branch, one pull request at the end)

## Goal
After this, the whole agent works end to end in the simulator. The receptionist presses "Run this week", the right braces patients get a warm English and Arabic reminder at a time between 17:00 and 22:00, patients see it on a phone screen, a repeat run adds nothing, patients who need a person land on a call list, the receptionist books a slot and the patient is told straight away, and a patient can ask "What times are available?" and get a tidy list.

## Features in this plan
F4 send times, F5 the phone simulator, F6 repeat-run safety and the second reminder, F7 the call list, F8 the receptionist's booking screen, F9 the booking confirmation, F10 the free-times reply, F11 the holding reply for anything else. F12 (run log) stays "later".
Acceptance criteria served: AC1 (send times, simulator), AC2 (repeat run, second reminder), AC3 (booking confirmation), AC1 and AC2 (call list), AC4 (confirmation wording), AC5 (replies).

## Shared pieces (built first, used by several features)
- **Stores.** A small `JsonStore` (file and in-memory versions, passed in like the approval store) for saved state: messages, call list, bookings. Real files live in `data/state/` and are git-ignored; tests use in-memory stores. A missing or damaged file means empty.
- **Effective data.** The seed `patients.json` and `slots.json` never change. Bookings are saved separately, and the app reads "seed plus bookings" (a booked slot is taken, a patient with a booking has a booking). So F2's rules see receptionist bookings with no change to F2.
- **Message records.** Each message has: id, patient id, direction (out or in), kind (reminder, confirmation, times_reply, holding_reply, patient_message), the text, the week it belongs to, the reminder number, the visit date and `sendAt`. Texts hold first names only; no phone numbers are copied into messages, and nothing is logged to the console.
- **Language.** A reply is in Arabic if the patient's message has Arabic letters, else English (plain pattern, same idea as liwan-desk). Reminders and confirmations are English and Arabic in one message.
- **Saved state is changed in one synchronous step.** Each store has an `update` that reads, checks and writes with no waiting in between, so two quick presses (a double-click on "Book" or "Run this week") cannot both pass a check before either saves. A test submits twice and expects one booking and one set of reminders.
- **A run record.** Every real run saves one record per patient it looked at (week, patient id, status such as `sent`, `already_sent`, `skipped_booked`, `needs_person`, and the reason), so "why did this patient get nothing last Monday?" always has an answer. This is the rule in CLAUDE.md; the run log screen (F12) stays "later".
- **Reminder number comes from what was really sent.** The real run counts saved reminders for the visit: number = reminders already saved plus 1, never above 2. A patient with two reminders and still no booking goes to the call list (B6). If a Monday was skipped, so a patient due in the F-14 window has fewer than two saved reminders, no late reminder is sent: they go to the call list with the reason `missed_reminders`, so the call list never says something false. The F2 preview keeps using dates alone.
- **Two wording sets, approved separately** on `/wording`: (1) the reminders (F3, done) and (2) replies and confirmations (new: confirmation, times-reply opening and closing, holding reply). Each has its own fingerprint and approval, and nothing is built from a set that is not approved. If the replies set is not approved: a booking is still saved but its confirmation is not created and the patient goes on the call list with the reason `confirmation_not_sent`; a patient's message is saved but no reply is created and the patient goes on the call list with the reason `wording_not_approved`. Both are tested. Approve both sets on `/wording` before the browser click-through. This keeps AC4 and B8 intact.

## F4: Send times (B5)

## F10: The free-times reply (B7, AC5)
- Steps: in `/phone` the patient can type a message. Code reads what it is about with plain keyword patterns in English and Arabic (asks for times, availability, or when they can come), in this order: (1) a message that names a specific time, date or weekday goes to the holding reply (F11) even if it also asks for times; (2) otherwise a times request is answered; (3) anything else goes to F11. Only a braces patient with no booking gets a times list; any other sender (not braces, or already booked) gets the holding reply and a call-list entry. For a times request, code builds the list from the effective calendar for the patient's visit Friday (the Friday of their latest reminder, or else their due date); if that Friday is full, the next Friday with free times is used and the reply says so; if there is no Friday with free times, the patient gets the holding reply and a call-list entry with the reason `no_free_times`. The reply is checked by code before it is saved (every time is a free calendar time, no price, nothing booked or confirmed); a failed check gives the holding reply and a call-list entry. The reply is a fixed warm opening, one time per line in order, and a closing question, in the patient's language. Done when the 2026-11-06 patient types "What times are available?" and gets the 12 times, and an Arabic message gets an Arabic reply.
- Checks: tests (B7): the list equals the calendar's free times exactly and nothing else is in the reply; a time booked by the receptionist is gone from the list; no price; no "booked" wording; Arabic in gives Arabic out; a mixed message ("Can I come Friday 18:00? What times are free?") gets the holding reply; a non-braces or already-booked sender gets the holding reply; a full Friday uses the next Friday; no free Friday at all gives the holding reply and `no_free_times`; a mixed Arabic and English message works; the patient's message text never changes the reply except for choosing English or Arabic.

## F11: The holding reply for anything else

Done when "How much is a filling?" gets no price, a holding reply, and shows on `/calls`.
- Checks: tests: a price question, a booking request ("Friday 18:00 please"), an unclear or empty message and an Arabic question all get the holding reply and a call-list entry; nothing is promised or confirmed.

## AI parts
None in this version. Everything is code and fixed approved wording, in what liwan-desk calls templates mode (`AI_MODE=templates`). No model is called, so cost is nothing and no keys are needed. Reading a patient's message uses plain patterns, not a model. Jev (to read messages more flexibly) and Claude (to write a warmer opening and closing around the code-built list) can be added later, behind the same functions; they need the owner to paste `TYPESAFE_API_KEY` and `ANTHROPIC_API_KEY` into `.env.local` (names only go in `.env.example`). ## Approval and data
- What leaves the solution: nothing real. Messages only go to the simulator.
- What allows a message: for reminders, the approved reminder wording; for confirmations and replies, the approved replies wording (own approval record and fingerprint). Without the record, the build refuses.
- A booking changes only the app's own saved state, by the receptionist, after a fresh server-side check that the slot is free (B8).
- Secrets: none needed.
- Personal data: all names, phones and messages are synthetic. Message records hold first names and patient ids only, never phone numbers; nothing is written to console logs; the saved state files are git-ignored.
- Accepted risk for this simulator-only version (same as before): the receptionist pages (`/wording`, `/run`, `/book`, `/calls`) and `/phone` have no login. Before real use they must go behind staff sign-in.
