# Plan: F4 to F11 (built as one stack, on this branch, one pull request at the end)

## Goal
After this, the whole agent works end to end in the simulator. The receptionist presses "Run this week", the right braces patients get a warm English and Arabic reminder at a time between 17:00 and 22:00, patients see it on a phone screen, a repeat run adds nothing, patients who need a person land on a call list, the receptionist books a slot and the patient is told straight away, and a patient can ask "What times are available?" and get a tidy list.

## Features in this plan
F4 send times, F5 the phone simulator, F6 repeat-run safety and the second reminder, F7 the call list, F8 the receptionist's booking screen, F9 the booking confirmation, F10 the free-times reply, F11 the holding reply for anything else. F12 (run log) stays "later".
Acceptance criteria served: AC1 (send times, simulator), AC2 (repeat run, second reminder), AC3 (booking confirmation), AC1 and AC2 (call list), AC4 (confirmation wording), AC5 (replies).

## Shared pieces (built first, used by several features)
- **Stores.** A small `JsonStore` (file and in-memory versions, passed in like the approval store) for saved state: messages, call list, bookings. Real files live in `data/state/` and are git-ignored; tests use in-memory stores. A missing or damaged file means empty.
- **Effective data.** The seed `patients.json` and `slots.json` never change. Bookings are saved separately, and the app reads "seed plus bookings" (a booked slot is taken, a patient with a booking has a booking). So F2's rules see receptionist bookings with no change to F2.
- **Message records.** Each message has: id, patient id, direction (out or in), kind (reminder, confirmation, times_reply, holding_reply, patient_message), the text, the week it belongs to, the reminder number, the visit date and `sendAt`. Texts hold first names only; no phone numbers are copied into messages, and nothing is logged to the console.
- **Language.** A reply is in Arabic if the patient's message has Arabic letters, else English (plain pattern, same idea as liwan-desk). Reminders and confirmations are English and Arabic in one message.
- **Two wording sets, approved separately** on `/wording`: (1) the reminders (F3, done) and (2) replies and confirmations (new: confirmation, times-reply opening and closing, holding reply). Each has its own fingerprint and approval, and nothing is built from a set that is not approved. This keeps AC4 and B8 intact.

## F4: Send times (B5)
- Steps: add `src/lib/schedule.ts` with `sendTimes(monday, count, runAt)`; show the planned time per patient in the `/run` list. Done when tests pass and `/run` shows a time on every "to send" row.
- Rule: reminders go out only from 17:00 to 22:00 clinic time (UTC+4) on the Monday. The run starts at 09:00 Monday by default (the simulator has no real clock; a `runAt` can be passed in tests). Start is the later of the run time and 17:00. N reminders are spread evenly from the start to 22:00, always before 22:00. A run after 22:00 rolls to the next day's 17:00 to 22:00. Times are saved with the +04:00 offset.
- Checks: `npm test` (B5): 12 reminders at run time 09:00 all fall from 17:00 to before 22:00, in order, spread out; at 19:30 all start from 19:30; after 22:00 they roll to 17:00 the next day; 0 reminders gives no times; 24 reminders all fit.

## F5: The phone simulator and "Run this week" for real
- Steps: add the message store; change "Run this week" to a server action that builds each reminder (needs the reminders wording approved, otherwise it stops with a plain message) and saves it with its send time; add `/phone` (pick a patient, see their chat, send times shown on each message). Done when running 2026-11-02 puts 12 bilingual reminders in `/phone` for those patients, and a run with the wording unapproved creates none.
- A reminder that fails its checks (B4) is not saved; that patient goes to the call list with the reason (F7).
- Checks: tests that a run saves exactly the decided reminders with the right text, visit date (the Friday of that week) and send time; refuses without approval; `/phone` shows the chat in the browser.

## F6: A repeat run adds nothing, and the second reminder (B3, B6)

- Checks: tests B3 (same week twice adds 0; at most one reminder per week; at most two per visit) and AC2 numbers on the seed.

## F7: The call list (B6)

## F8: The receptionist books a slot (B8)
- Steps: add `/book` (pick a braces patient and a free slot, press "Book"). The server checks again that the slot is free and the patient has no booking, then saves the booking; a taken slot is refused with a plain message and nothing is saved. Done when booking P001 into 2026-11-06 at 18:00 takes 18:00 off the free list and booking 18:00 again for another patient is refused.
- Checks: tests: books a free slot; refuses a taken slot; refuses a second booking for the same patient; a booked patient is skipped by the next run (B2).

## F9: The booking confirmation (B8, AC3, AC4)
- Steps: when a booking is saved, build the confirmation from the booking record only (first name, the slot's day and time, Liwan Dental, English and Arabic in one message) and save it as a message at once (not held to the 17:00 to 22:00 window). If the replies-and-confirmations wording is not approved, the booking is still saved and the screen says the confirmation was not sent because the wording is not approved. Nothing is created for a refused booking. Done when booking in F8 shows a warm confirmation in `/phone` naming "Friday 6 November" and "18:00", with no later reminders for that patient.
- Checks: tests that the day and time come from the booking, the checks catch a wrong time, no price, no confirmation for a refused booking, none without approval; `/phone` shows it.

## F10: The free-times reply (B7, AC5)
- Steps: in `/phone` the patient can type a message. Code reads what it is about with plain keyword patterns in English and Arabic (asks for times, availability, or when they can come). For a times request, code builds the list from the effective calendar for the patient's visit Friday (the Friday of their latest reminder, or else their due date); if that Friday is full, the next Friday with free times is used and the reply says so. The reply is a fixed warm opening, one time per line in order, and a closing question, in the patient's language. Done when the 2026-11-06 patient types "What times are available?" and gets the 12 times, and an Arabic message gets an Arabic reply.
- Checks: tests (B7): the list equals the calendar's free times exactly and nothing else is in the reply; a time booked by the receptionist is gone from the list; no price; no "booked" wording; Arabic in gives Arabic out; the patient's message text never changes the reply except for choosing English or Arabic.

## F11: The holding reply for anything else
- Steps: any message that is not clearly a times request, or that asks for a specific time to be booked, gets a kind holding reply in the patient's language ("thank you, I have passed this to our receptionist, who will reply shortly"), with no answer to the question, and the patient goes on the call list with the reason "other question". Done when "How much is a filling?" gets no price, a holding reply, and shows on `/calls`.
- Checks: tests: a price question, a booking request ("Friday 18:00 please"), an unclear or empty message and an Arabic question all get the holding reply and a call-list entry; nothing is promised or confirmed.

## AI parts
None in this version. Everything is code and fixed approved wording, in what liwan-desk calls templates mode (`AI_MODE=templates`). No model is called, so cost is nothing and no keys are needed. Reading a patient's message uses plain patterns, not a model. Jev (to read messages more flexibly) and Claude (to write a warmer opening and closing around the code-built list) can be added later, behind the same functions; they need the owner to paste `TYPESAFE_API_KEY` and `ANTHROPIC_API_KEY` into `.env.local` (names only go in `.env.example`). Whatever a patient writes would only ever be passed to a model as quoted data, never as instructions, and model output would go through zod before use.

## Approval and data
- What leaves the solution: nothing real. Messages only go to the simulator.
- What allows a message: for reminders, the approved reminder wording; for confirmations and replies, the approved replies wording (own approval record and fingerprint). Without the record, the build refuses.
- A booking changes only the app's own saved state, by the receptionist, after a fresh server-side check that the slot is free (B8).
- Secrets: none needed.
- Personal data: all names, phones and messages are synthetic. Message records hold first names and patient ids only, never phone numbers; nothing is written to console logs; the saved state files are git-ignored.
- Accepted risk for this simulator-only version (same as before): the receptionist pages (`/wording`, `/run`, `/book`, `/calls`) and `/phone` have no login. Before real use they must go behind staff sign-in.

## What could break
The riskiest part is changing "Run this week" from a preview into a real run that saves messages, because F2's counts and F6's repeat safety must stay exact. The seed numbers are tested at every step (12, 24, 24, and 12 on the call list). Reading "seed plus bookings" could change what F1 and F2 see; their existing 60 tests must keep passing.
